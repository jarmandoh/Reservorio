# Evaluación del frontend y plan de mejora

**Fecha:** 05/10/2026  
**Alcance:** frontend Angular, seguridad del navegador, configuración de compilación, pruebas automatizadas y flujo de CI.  
**Método:** revisión estática y ejecución local del build de producción y pruebas unitarias. No equivale a una prueba de penetración ni a una auditoría completa WCAG.

## Resumen ejecutivo

La aplicación utiliza Angular 22, rutas lazy-loaded, Tailwind, GSAP, Leaflet, service worker y Playwright. La compilación de producción se completó correctamente. Antes de los cambios, las 9 pruebas unitarias existentes pasaban. El bundle inicial observado fue de 513.67 kB sin comprimir (135.90 kB de transferencia estimada), dentro de los presupuestos actuales.

Se encontró y corrigió un redirect inseguro en los flujos de pago: el cliente navegaba directamente a `checkoutUrl`, aunque esa URL viene de una respuesta remota. También se identificaron oportunidades de mejora en cobertura/gates de CI, accesibilidad, pruebas móviles, resiliencia offline, rendimiento y SEO.

### Cambio aplicado y evidencia

- Los dos flujos validan la URL antes de asignarla a `window.location.href`.
- La validación parsea la URL, solo admite HTTP(S), requiere HTTPS por defecto y compara el `origin` exacto con una allowlist. El valor productivo predeterminado es `https://checkout.stripe.com`; un origen parecido o con sufijo adicional no coincide.
- Si la URL falta, está malformada, usa un esquema no permitido o no coincide con la allowlist, la navegación se bloquea y se muestra un error recuperable. En desarrollo, HTTP solo puede habilitarse mediante una allowlist explícita.
- El backend también valida `successUrl` y `cancelUrl` antes de crear el pago: solo acepta el origen de `FRONTEND_URL` y las rutas de retorno de pago correspondientes; en producción exige que ese origen sea HTTPS. Esto evita que una llamada directa a la API use el checkout de Stripe para redirigir a un sitio externo.
- Se añadieron pruebas para origen aprobado, producción HTTPS, origen externo, HTTP en producción, `javascript:`, URL ausente/malformada, spoofing por sufijo y fallo cerrado sin allowlist.
- Se verificó el rechazo del origen externo en el backend antes de insertar el pago, así como el caso permitido del frontend configurado.
- Verificación posterior: pruebas del helper (**9/9**), suite frontend completa (**18/18**), suite backend específica (**11/11**) y `pnpm build` aprobados.

La validación frontend no reemplaza controles backend: el servidor debe seguir verificando autorización, estado del pago, webhooks y datos del negocio.

## Oportunidades de mejora

### Calidad, cobertura y CI

- Hay pocos archivos de pruebas unitarias frontend; ampliar pruebas para guards, sesiones, servicios HTTP, validaciones y estados de error.
- En [.github/workflows/ci.yml](.github/workflows/ci.yml), la etapa `Unit tests with coverage` tiene `continue-on-error: true`; fallar en cobertura no bloquea el merge. Definir un umbral incremental alcanzable y convertirlo en gate.
- [playwright.config.ts](frontend/playwright.config.ts) configura solo Chromium. Añadir navegador y viewport móvil según la matriz de soporte, priorizando reserva, pagos y acceso a paneles.
- Aislar y limpiar los datos E2E; cubrir errores de API, reintentos, expiración de sesión, pérdida/restauración de red y concurrencia de disponibilidad.

### Accesibilidad y experiencia

- [styles.css](frontend/src/styles.css) oculta las barras de desplazamiento globalmente. Revisar con teclado, trackpad y usuarios de baja visión si esto elimina una señal útil de contenido desplazable.
- Incorporar comprobaciones axe para rutas públicas y tareas críticas, además de revisión manual con teclado y lector de pantalla: foco visible y restaurado, etiquetas, errores de formularios, contraste, zoom y reflow.
- El shell en [app.component.ts](frontend/src/app/app.component.ts) contempla `prefers-reduced-motion` en las animaciones de navegación; verificar que las animaciones de componentes y estados de carga también lo respeten.
- Establecer estados coherentes de carga, vacío, éxito, error recuperable y reintento. No depender solo de un toast para comunicar errores importantes.
- Probar la reserva completa en pantallas pequeñas y con teclado virtual, incluyendo el retorno desde el proveedor de pagos sin perder el progreso.

### Resiliencia, rendimiento y PWA

- Medir LCP, INP y CLS en home y reserva, en móvil y red lenta. El tamaño del bundle no representa por sí solo el rendimiento percibido.
- Mantener el presupuesto actual como control inicial y fijar metas adicionales según mediciones. Comprobar que Leaflet, actualmente separado en un chunk, solo se descargue cuando se necesita.
- Probar service worker en staging: primera carga, actualización, desconexión/reconexión, sesión caducada y disponibilidad obsoleta. Nunca presentar disponibilidad o pagos cacheados como confirmación actual.
- Revisar fallos de navegación y renovación de sesión para que se comuniquen de forma recuperable y queden observables sin registrar PII o secretos.

### SEO y publicación

- Sustituir dominios de ejemplo en canonical, sitemap y robots por el dominio real. Excluir login, paneles y rutas de pago de indexación.
- Evaluar prerender/SSR para fichas públicas de negocios; validar metadatos y datos estructurados con información real.
- Verificar CSP, TLS, cabeceras y proxy en staging y producción; confirmar que checkout, mapas y recursos necesarios funcionan antes de ajustar políticas.

## Paso a paso recomendado

### Fase 1 — Seguridad de checkout (completada)

1. Reproducir el redirect no validado y comprobar el impacto con pruebas negativas de origen/esquema y sin inserción de pago cuando el retorno apunta a un host externo.
2. Validar URLs frontend con parseo estricto y comparación exacta de origen; exigir HTTPS en producción y fallar de forma cerrada.
3. Validar también en el backend las URL de retorno que se envían a Stripe: mismo origen de `FRONTEND_URL`, rutas correctas y HTTPS si `NODE_ENV=production`.
4. Añadir pruebas positivas y negativas, incluyendo esquema inseguro, URL malformada, origen externo, spoofing, allowlist ausente y origen de retorno externo.
5. Confirmar que ambos flujos de pago frontend usan la validación compartida.
6. Repetir pruebas y build: **9 pruebas del helper, 18 pruebas frontend, 11 pruebas backend específicas y build aprobados**.

### Fase 2 — Fortalecer el gate de frontend

1. Quitar `continue-on-error` del paso de cobertura.
2. Medir la línea base y definir umbral incremental para frontend.
3. Añadir tests para guards, sesiones, servicios, errores HTTP y formularios.
4. Extender E2E a fallos de API, expiración, pagos cancelados, reintentos y reconexión.
5. Añadir navegadores y viewports que correspondan al soporte declarado.

**Estado:** gates y cobertura configurados; smoke tests locales aprobados. La suite E2E que crea datos se deja para CI/una base aislada, no para la base local compartida.

**Evidencia de ejecución (05/10/2026):**

- Cobertura frontend obligatoria en CI, sin `continue-on-error`, con umbrales globales incrementales: 36% statements, 33% branches, 22% functions y 38% lines.
- Suite unitaria con cobertura: **35/35** pruebas aprobadas; resultado **36.93% statements, 33.84% branches, 22.34% functions y 38.58% lines**, por encima de los cuatro umbrales.
- Build de producción aprobado; bundle inicial **514.74 kB** (136.08 kB de transferencia estimada).
- Playwright descubre **22 tests en cinco proyectos**: Chromium E2E, WebKit smoke, Chromium smoke, Chromium accesibilidad y Chromium móvil. La batería browser aislada —sin los cinco E2E que mutan datos— terminó con **17/17 aprobados**: 13 checks de accesibilidad/interacción, dos smoke tests Chromium, uno móvil y uno WebKit.
- El check WebKit confirma que se sirve el documento HTML; en este entorno la app Angular se cerró de forma intermitente al inicializarse con WebKit, así que no se presenta como validación funcional completa del SPA en Safari.
- El smoke de conectividad emite eventos `offline`/`online` del navegador y valida el banner y recuperación de la interfaz. No desactiva la red real del contexto Playwright.
- La suite E2E de reserva y administración crea negocios, servicios, reservas y clientes. No se ejecutó contra el backend local para evitar mutar una base posiblemente compartida; CI la configura con PostgreSQL efímero y debe aportar esa evidencia al ejecutarse.
- El `format:check` global local todavía señala formato en archivos preexistentes y artefactos generados de Playwright. Los archivos nuevos de prueba de pago y del helper de checkout se formatearon y su comprobación focalizada pasa; no se reformatearon archivos ajenos a esta fase.

**Criterio de salida:** un build o test fallido bloquea el merge; los flujos críticos tienen evidencia reproducible. La aprobación final de la suite E2E integral depende del job de CI con su PostgreSQL efímero.

### Fase 3 — Accesibilidad y UX móvil

1. Ejecutar axe en home, reserva, login, panel y confirmación de pago.
2. Corregir primero bloqueos de teclado, foco, nombres accesibles, contraste y errores de formulario.
3. Completar revisión manual con teclado y lector de pantalla; probar zoom y reflow móvil.
4. Revisar movimiento reducido y barras de desplazamiento.
5. Validar con usuarios el flujo de reserva y la recuperación desde errores/red interrumpida.

**Estado:** correcciones de código y comprobaciones automatizadas completadas; validación manual con NVDA/lector de pantalla y pruebas moderadas con usuarios quedan pendientes, ya que requieren interacción y participantes reales.

**Cambios aplicados:**

- Se incorporó un enlace para saltar al contenido y un landmark `<main>` compartido; el foco pasa al contenido tras navegaciones internas, sin robar foco en la carga inicial.
- Se restituyeron las barras de desplazamiento nativas (antes se ocultaban globalmente) y se agregó un indicador de foco visible de alto contraste.
- Se reemplazaron tarjetas de negocio con `role="button"` por enlaces nativos a la ruta de reserva; los filtros comunican su estado con `aria-pressed`.
- El menú de cuenta se puede abrir/cerrar con teclado y devuelve el foco al disparador con Escape.
- Se añadió soporte global `prefers-reduced-motion`, incluidas animaciones, transiciones y scroll animado.
- Se corrigió contraste AA en texto neutro y en la selección del tipo de cuenta. Los errores de login/registro ahora quedan asociados a sus campos mediante `aria-invalid` y `aria-describedby`; estados de error/carga se exponen a tecnologías de asistencia.
- Los formularios de login obtuvieron etiquetas autocomplete y mensajes asociados para errores de email, teléfono, PIN y código.

**Evidencia automatizada (05/10/2026):**

- Axe (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`): **sin violaciones detectadas** en home, reserva, login de cliente/admin/negocio, creación de cuenta, panel admin y pago cancelado, en los estados probados.
- Teclado: enlace skip y foco visible, apertura/cierre del menú con Escape y restauración del foco; mensajes de validación enlazados a sus campos.
- Reflow en Chromium a 640 px (viewport equivalente a 200% desde 1280 px) y 320 px: home y reserva sin scroll horizontal del documento.
- `prefers-reduced-motion`: se comprobó la reducción de duración de animaciones. Se retiraron las reglas globales que ocultaban scrollbars.
- Browser aislado: **17/17** aprobados; tests unitarios con cobertura **35/35**; build de producción aprobado.

El escaneo de axe es automatizado y no equivale a certificación WCAG ni cubre todos los estados/datos posibles. **No se realizó una sesión manual con NVDA/lector de pantalla ni pruebas moderadas con usuarios**, por lo que el criterio de salida queda parcialmente abierto hasta registrar esa evidencia.

### Fase 4 — Rendimiento y funcionamiento offline

1. Capturar Lighthouse y Web Vitals de referencia en staging para home y reserva.
2. Priorizar optimizaciones según datos: carga inicial, imágenes/fuentes, trabajo del hilo principal y descarga del mapa.
3. Validar las metas LCP/INP/CLS bajo red lenta y registrar antes/después.
4. Probar actualización del service worker, assets obsoletos, reconexión y sesión caducada.

**Estado (05/10/2026):** se completó la corrección y validación automatizada local del shell offline, la reconexión y el cierre de sesión por 401. La aceptación de Core Web Vitals y la actualización entre dos releases del service worker siguen pendientes de staging, pues requieren dominio, red móvil/CPU limitadas y dos versiones desplegadas.

**Cambios aplicados:**

- El service worker conserva la caché del shell estático y no trata respuestas API variables como datos offline actuales; la caché local de GET público vence y no sustituye errores reales cuando hay conexión.
- Las pruebas de navegador ahora recargan realmente el shell sin red y comprueban la recuperación al reconectar. La prueba 401 comprueba en paralelo el aviso transitorio, el envío de la sesión y su eliminación del almacenamiento.
- El servidor local de Playwright entrega `index.html` y sus assets sin modificarlos, preservando los hashes del manifiesto Angular; `/api` se reenvía al backend en el mismo origen para evitar CORS. El servidor de pruebas usa por defecto el puerto 4201 y no reutiliza un `ng serve` arbitrario. Se añadió al control de versiones la configuración Playwright, antes excluida por `.gitignore`.
- El build de producción mantiene el mapa en un chunk lazy y el chunk inicial resultó **441.33 kB bruto / 111.23 kB estimado transferido**, bajo el presupuesto actual.

**Evidencia local (05/10/2026):**

- Build de producción aprobado.
- Chromium, smoke, accesibilidad, responsive móvil y WebKit smoke: **19/19** aprobados; incluye shell offline, reconexión y sesión 401.
- Unit tests: **38/38** aprobados; Prettier focalizado en los archivos modificados aprobado.
- Referencia sintética en Chromium de escritorio contra localhost, sin limitación de red: LCP **280 ms**, CLS **0.0000**, mayor duración de evento observado **16 ms** (25 entradas), transferencia del documento **23,026 bytes**. Es solo un chequeo de laboratorio y **no equivale a Lighthouse ni a Web Vitals de campo**.

**Pendiente externo para cerrar la fase:** ejecutar Lighthouse/Web Vitals en staging para home y reserva en móvil/red lenta y guardar la comparación; desplegar dos versiones consecutivas para verificar actualización del worker y recuperación de chunks anteriores/obsoletos. No se fijaron umbrales CWV con la única medición localhost, porque no sería representativa.

### Fase 5 — SEO y release

1. Configurar el dominio canónico, sitemap, robots y metadatos de páginas públicas.
2. Decidir SSR/prerender para fichas públicas y validar datos estructurados verificables.
3. Hacer smoke tests de rutas profundas, API, TLS, CSP, mapas y checkout en staging.
4. Guardar evidencia de CI, seguridad, accesibilidad, Web Vitals y smoke tests antes de publicar.

**Estado (05/10/2026):** implementada la configuración SEO local y la decisión arquitectónica. Pendiente el smoke de `https://staging.reservorio.app`, TLS/CSP detrás de Caddy/Nginx y la evidencia final de CI/release: el DNS de `reservorio.app` y del host staging no resuelve desde este entorno; Docker Desktop tampoco está disponible para ejecutar Nginx/Caddy aquí.

**Cambios aplicados:**

- `https://reservorio.app` queda como origen canónico. `robots.txt` ya no contiene el placeholder y el sitemap XML incluye solo home y privacidad, sin `lastmod` inventado.
- El título, descripción, canonical y Open Graph se gestionan por ruta. Solo home y privacidad se indexan; reserva, pago, cuenta, login, paneles y rutas desconocidas se marcan `noindex, nofollow`. Nginx añade `X-Robots-Tag` en las respuestas directas para que los robots reciban la regla incluso en la primera carga SPA.
- No se implementa SSR/prerender todavía: no existe una ficha pública de negocio; home depende del listado API dinámico y las demás rutas relevantes son transaccionales/privadas. Reconsiderarlo cuando existan páginas públicas indexables con datos verificables, para evitar generar contenido estructurado o disponibilidad que no corresponda.
- Se corrigió la CSP de Nginx para permitir las hojas de estilo externas de Google Fonts que ya enlaza `index.html`; sin ese origen las fuentes e iconos eran bloqueados.
- Se documentó en [DEPLOY.md](DEPLOY.md) el host canónico, valores de dominio/CORS, la decisión SPA y el procedimiento de smoke para staging, sin completar pagos reales.

**Evidencia local (05/10/2026):** build de producción aprobado; **21/21** pruebas browser (smoke, SEO, offline, sesión, accesibilidad, móvil y WebKit smoke) aprobadas; **41/41** pruebas unitarias aprobadas; Prettier focalizado aprobado. El test SEO valida sitemap, robots, canonicals, metadatos y `noindex` en rutas de reserva. No valida la respuesta de Nginx/Caddy desplegado.

**Pendiente antes de release:** aprovisionar DNS y TLS para `reservorio.app` y `staging.reservorio.app`, ejecutar el procedimiento de staging documentado, confirmar headers y API/Stripe/mapas reales, archivar resultados con SHA del commit y enviar el sitemap desde Search Console con el dominio verificado. El pago se prueba únicamente en modo Stripe de prueba. La fase y el release permanecen abiertos hasta aportar dicha evidencia.

**Criterio de salida:** ningún hallazgo crítico/alto abierto, ningún fallo en flujos críticos y ninguna información de negocio o pago desactualizada presentada como vigente.
